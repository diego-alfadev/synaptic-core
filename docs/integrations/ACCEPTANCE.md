# Host acceptance for the candidate

Status: test protocol, not a completed integration claim. Use an isolated synthetic workspace.
Do not update an editor, enable trust, change global settings or use a real engagement repository
as a side effect of running this protocol. Installation permission and host trust are separate.

## Validate the synthetic inputs first

The fixture must satisfy the selected release's brain contract before evaluating an agent against
it. Byte-for-byte preservation alone does not establish valid schema or complete node metadata.
Where Node is already permitted, use the trusted pinned candidate's `tools/check.js <fixture-brain>`
and retain its exit status and findings before the host run. If a runtime is unavailable, inspect
the required fields and source/index links against that candidate's contract and record that the
automated check was not run. Keep expected answers outside the agent workspace and conversation.
Resolve fixture defects before treating a failed resume as a host or product failure. Passing lint
does not establish correct facts, useful curation, loading, native firing or cold retrieval.

## What a supported profile must record

Record the exact release/source commit, brain/schema, workspace scope, host distribution/version,
agent harness/version, selected capabilities, permission constraints and check time. A chosen model
does not identify the harness. Keep source evidence and the changed configuration with the result.
Record the effective hook inventory too: project hooks add to user/system hooks; they do not replace
them. Review the prepared project hook through the host's normal trust flow, without auto-trusting it.

For each capability record selection, observed state, trigger, executor, evidence time/configuration,
fallback and last outcome. Do not infer "agent loaded" from file presence, "MCP connected" from its
configuration or "automatic capture" from a manually run script. No independent observer means
last-check evidence, not continuous health. Off is a valid state for an optional component.

## Codex here

Prepare the reviewed bundle and synthetic files first. A real fresh chat must prove carrier loading
before it reads tools/files, then use the seeded sources to resume three known facts. An inherited
subagent or a model that was just told the answers does not supply that proof. Record loading and
source-based resume separately. No paid API/headless batch is needed for this protocol.

Exercise the selected assisted or native-event profile, then start another fresh session and ask it
to retrieve the saved result. Record the paths it actually used and compare against expected facts.

The optional Codex curation profile has an additional live gate:

1. A normal host turn, with an explicitly selected changed source, reaches the genuine native Stop
   event. The model must not manually invoke the adapter to manufacture firing evidence.
2. The synchronous event adapter issues at most one continuation. The existing permitted agent
   produces a useful source-grounded curation draft and provenance, not just a success marker.
3. The subsequent event verifies the persisted artifact against the request and unchanged source
   fingerprints. Inspect the result for correct meaning, deduplication and any unresolved conflict.
4. A fresh session discovers and retrieves that result. State that it is a curated draft, with
   promotion pending; this does not demonstrate automatic wiki consolidation or universal recall.
5. Repeat with unchanged sources: no needless curation. Exercise invalid/missing output, interrupted
   work and denied writes: no retry loop, no false success, pending work retained and visible.
6. Exercise disabled/no-hook operation: assisted operation remains explicit. No MCP is needed for
   this adapter; Node commands and native hook permission are needed for this particular profile.

Synthetic adapter tests prove state transitions, confinement and persistence checks. Only the real
event/model/result/second-session drill supplies live evidence. Structural validity does not prove
semantic accuracy, and the local checker is not an independent security boundary against its agent.

## Owner-run VS Code pilot

The owner tests in the chosen environment from a clearly labelled GitHub RC after Codex and package
preparation. Collect actual editor/distribution, extension/harness and policy constraints then.
Selecting a model in VS Code does not make another host's hook configuration applicable.

- Upgrade an existing synthetic brain from the exact page, with staging, diff and byte-faithful
  backup. Preserve newer knowledge and rules; verify same-version missing/modified content too.
- Prove fresh loading, ordinary operation/argument routing, useful capture and another cold resume.
- Exercise no-MCP operation without repeated installation attempts. Where no hooks/commands are
  allowed, demonstrate and label assisted capture and manual checks.
- For each optional capability actually selected, prove genuine event firing or host discovery/use.
  Test stopped/missing server, unavailable runtime, rejected permission and changed configuration.
- Restore the upgraded targets without replacing newer knowledge. A subsequently edited target
  requires a reviewed restore, not an automatic overwrite.

## Release decision

The first stable requires the coherent documented journey, the real VS Code pilot and at least one
supported profile with bounded native-event/model curation, checked persisted output and visible
failure. Restricted profiles can remain assisted. A narrow curated-draft result must be named as
such; it cannot support a claim that the whole wiki maintains itself. A failed pilot yields a new
candidate rather than changed bytes under the same release identity.

RC sequence approval is not publication permission. Merge, each push, tags and releases retain their
separate authorisation. Fill evidence and actual versions before making support claims.
