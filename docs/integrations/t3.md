# T3 Code thin project integration

Status: prepared CORE procedure and pilot protocol; live T3 acceptance pending. This guide does not configure or install T3. It covers one selected local existing-login Codex or Claude instance and a synthetic project brain. Managed accounts, shadow homes, remote execution, worktrees, global/private reach and native hooks stay outside the initial cut.

The standalone [T3 procedure](../../standalone/synaptic/references/t3.md) is the adapter contract. A permitted file-capable agent can follow it without adding Node, MCP or a Synaptic daemon. The current `tools/setup.js` remains a VS Code utility; it does not acquire a T3 host mode merely because this procedure exists. Do not run its Copilot planner against a T3 workspace.

## Select the actual instance

T3 delegates work to a provider instance. Record the actual T3/server version, execution machine, selected provider kind/id, provider version, effective home, project root and cwd. A terminal Codex home, account label or chosen model does not establish what T3 uses. Read only bounded non-secret selected-instance metadata; do not print full T3 settings, environment/arguments, authentication or transcripts.

Choose the existing manually configured instance already authenticated by the owner. This pilot performs no login, trust/policy change, account switch or provider installation. Unknown selection or execution paths remain unresolved; prepare a record of missing facts rather than inventing defaults.

| Thin profile | Project files available for a concrete plan | Required qualification |
| --- | --- | --- |
| T3 with existing Codex | The effective project `AGENTS.md` or `AGENTS.override.md`; optionally the exact `.agents/skills/synaptic/` package inventory. | Resolve root-to-cwd overrides and selected provider discovery before selecting a destination. |
| T3 with existing Claude | Existing project bridge and only the required owned import in the effective Claude carrier; optionally the exact `.claude/skills/synaptic/` inventory. | Preserve imports and inspect config-directory skill precedence. Do not create a second competing engine. |

The plan also names its brain-local `harness/setup/t3-<provider>.md` record. T3 settings, user/global provider config, hook/MCP/authentication files and managed/shadow state are excluded. Project carriers use project-relative pointers; private/global pointers never become a repo workaround.

## Review one concrete change

Use a complete source-pinned package. Prepare a new private stage with the exact candidate files, diff and byte-faithful backups. Enumerate every destination, including each skill file; “copy the folder” is insufficient. State which fields are owner declarations and which configuration facts were inspected.

The selected target remains independent of what the current plan configures. The strongest thin profile is files/bridge plus a verified project skill where discovery is supported; capture and consolidation remain assisted. Command menus, MCP and native continuation are not silently enabled. Prior refusals and deferred goals remain intact and visible.

Approval must cover the exact plan and rollback. Recheck selected instance/home/cwd, current decisions including any newly created intent, policy constraints and destination preimages just before apply. Stale approval cannot reopen a later refusal. On interruption retain the plan/preimages and restore only touched targets whose bytes still match this transaction. Preserve newer knowledge and user edits.

## Run the isolated pilot

Use [the pilot specification](../specs/t3-core-pilot.md) and [record template](../../standalone/synaptic/templates/templates/t3-pilot.md). The fixture contains synthetic facts, empty task/pending state and no live brain copy. A real fresh T3 session must establish any claim about initial loading; reading sources later proves only that those reads worked.

The pilot separately exercises:

- The selected project carrier and skill/operation arguments without repeated setup.
- Useful explicit assisted capture/consolidation and retrieval in another fresh T3 session.
- Deferred target visibility through a passive consolidation notice, without prompts or repair.
- Denied writes, changed preconditions and rollback preserving later knowledge/owner edits.

The optional zero-read `synaptic ping` is a user-initiated observation, not a setup-completion gate. An agent inherited from the setup chat or told the fixture answers is not cold-loading proof. Native Stop is unknown in this thin profile. T3's own Claude SDK Stop callback does not establish that a separately configured CLI hook fires or coexists correctly.

Report **configured project files**, **effective configuration** and **observed execution** separately. Mark unsupported/uninspected cases explicitly. A passing fixture or documentation review cannot support every T3/provider version, remote environment or account configuration.

## When this thin scope is insufficient

For Claude, upstream T3 reads an append-system-prompt file and carries its text into the SDK append value. This is a possible later integration route, not permission to edit T3 launch settings now. Codex uses an effective home and app-server arguments that may differ from a terminal invocation. Shadow homes introduce intentional links and separate authentication; do not bypass general path protections to make one pass.

An expanded adapter needs its own exact destinations, preservation tests and real-host observations. Keep worktrees separate: a non-versioned `.synaptic` directory may be absent after cwd moves into a worktree. Diagnose the pointer instead of copying private memory or creating another brain.

Primary evidence is pinned in the standalone procedure to T3 source `134580067f3c811f32630667bd57f048d0bff9ee`. The installed pilot versions and final evidence status belong in its record, not in a general support claim.
