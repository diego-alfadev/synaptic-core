# T3 Code CORE pilot specification

Status: prepared for owner-selected execution; no live pilot has run. This specification supplies an isolated fixture and a reviewable plan boundary. It does not authorise active host configuration, publication or a new executable adapter framework.

## Outcome and boundary

Demonstrate that one selected local T3 existing-login provider can use a project brain through its normal project carriers and optional skill, capture explicitly and retrieve useful saved knowledge in a later session. The baseline succeeds independently of optional menus, hooks/MCP and loading proof.

Choose Codex or Claude after the owner identifies the actual instance and execution machine. Exclude managed ChatGPT, shadow homes, remote hosts, worktrees, global/private brains and native hook activation from this first cut. These are different acceptance cases, not failed attempts at the thin profile.

## Prerequisites to resolve before a write plan

| Fact | Evidence required |
| --- | --- |
| T3 installation and provider | Actual selected environment/instance, versions and existing manual-login mode; model selection alone is insufficient. |
| Execution paths | Provider binary, effective provider home, project root and cwd from bounded non-secret facts; mark declarations distinctly. |
| Ownership and constraints | Owner-controlled synthetic location, permitted file writes and relevant policy; no trust or policy changes during the test. |
| Package | One complete exact candidate/release and trusted source identity/inventory, privately staged. |
| Existing decisions | Known refusals/targets/deferrals; unknown history stays unknown. |

Do not identify an account by reading authentication or serialising T3's full settings/environment. If the selected environment is on another machine, prepare the fixture and plan there with permitted tools; local preparation is not remote acceptance.

## Synthetic fixture

Create a fresh owner-approved directory, for example `synaptic-t3-pilot`, in an isolated local test location. Generate a new synthetic brain from the selected package's templates, not from the live brain. Fill required template fields and MOC links; no scaffold placeholder should be treated as real knowledge. The fixture inventory is:

| File | Purpose and fixed synthetic content |
| --- | --- |
| `.synaptic/BRAIN.md` | Schema1.0 synthetic project brain; retain normal navigation/capture instructions. |
| `.synaptic/knowledge/INDEX.md` and `pilot/_index.md` | Route only to the synthetic fixture node. |
| `.synaptic/knowledge/pilot/restore-plan.md` | Valid node frontmatter plus: “The test archive is kept offline. The restore rehearsal is scheduled for Thursday. The next action is to compare the restored manifest.” |
| `.synaptic/journal/_current.md` | Synthetic resume pointer to that node; no copied real-session log. |
| `.synaptic/harness/setup/t3-<provider>.md` | Pilot selection, target/configured state and evidence record from the reviewed plan; use the record template. |
| Selected provider carrier and skill files | Only files enumerated by the concrete plan in the standalone T3 procedure. |

Keep expected answers in the reviewer's private test notes, outside the carrier, first request and any transcript supplied to the agent. A skill installation must contain the selected package's complete manifest/receipt, not a synthetic substitute that cannot execute the actual procedure.

## Review and execution sequence

1. **Inspect read-only.** Resolve selected instance/home/cwd, carriers, scope and known decisions. Record exclusions and unknowns. Do not modify T3 settings, provider user/global files, authentication, hooks or MCP.
2. **Prepare privately.** List exact candidate files, source identity, owned marker regions, destination preimages including absence, semantic preconditions, expected checks and rollback. A complete skill means every individual manifest entry is enumerated.
3. **Owner review.** Review the bounded diff before configuration writes. Approval applies to that plan only. If the owner chooses an assisted/files-only target, preserve it; explain any carrier/skill limitation rather than silently raising it.
4. **Apply recoverably.** Recheck current instance/provider/home/cwd, policy, target/refusal state and destination bytes. Abort a stale plan before writing. Record completed steps; interruption is visible pending work, not permission for automatic retry.
5. **Check files.** Verify exact inventory/content and preservation of unrelated bytes/line endings, settings, other instances and newer knowledge. Record project configuration separately from effective/observed state.
6. **Optional cold loading observation.** If the owner elects a user-initiated `synaptic ping`, issue it in a genuinely fresh selected T3 session before any reads/tools. Keep the scoped transcript. Setup itself never requests this or uses it as a completion condition. Otherwise loading remains unknown.
7. **Source-based resume.** In the intended T3 session ask it to resume the synthetic project and identify the next action from saved sources. Inspect the actual source paths and accuracy. Do not paste expected answers into the request.
8. **Skill and arguments.** Invoke the selected actual Synaptic skill/operation with an argument appropriate to its contract. Record whether T3 routed the intended operation/argument and whether it read the correct source. A rendered menu alone is insufficient.
9. **Assisted capture and consolidate.** Explicitly introduce one new synthetic durable fact: “A successful restore comparison must include the archive checksum.” Ask for capture/consolidation through normal procedures. Inspect the persisted meaning, source provenance and links. Confirm one passive pending-pool notice, without interactive setup, broad discovery or repair. This tests model behaviour rather than deterministic semantic judgment.
10. **Cold retrieval.** Start another fresh selected T3 session and ask for the restore comparison rule without supplying it. Record actual retrieval and correctness separately from carrier loading. A source read or answer from the previous model context is not cold retrieval.
11. **Failure and recovery.** In separate synthetic copies, exercise denied destination writes; destination/intent changes after planning; an unreachable brain; and a later owner edit before rollback. Confirm no false success or retry loop and no overwrite of later edits. A changed refusal requires a reviewed new plan, not reuse of old approval.

Native Stop/event coexistence is not part of thin-profile success. If separately authorised, test a genuine event from a normal host turn without manually invoking the adapter; record T3/provider versions, actual dialect, event source and bounded output. A callback registered in upstream code or a passing synthetic event fixture is not that observation.

## Acceptance matrix

| Claim | Passing evidence | Never sufficient |
| --- | --- | --- |
| Package installed | Exact inventory/content comparison with selected source. | Version header or files present. |
| Baseline configured | Scope-safe bridge in the resolved effective carrier; applicable configuration facts recorded. | Creating another brain or carrier to hide unresolved scope. |
| Initial carrier loaded | Separately elected fresh-session, pre-read observation with matching scope and source. | A later file read, inherited agent or self-report after setup. |
| Skill/argument use | Real selected T3 request routes the operation and argument and uses the correct sources. | A skill file or command menu exists. |
| Assisted knowledge useful | Persisted source-grounded result plus accurate retrieval from a later cold session. | Schema-valid Markdown or a success marker. |
| Passive notice | Each observed consolidation emits one scoped snapshot-based notice; no setup action begins. | Source text only; a reminder that triggers discovery. |
| Safe failure/rollback | Pending diagnosis retained; stale plans refused; only owned unchanged bytes restored; newer knowledge preserved. | Restoring a whole old brain or silently discarding failures. |
| Native hooks/MCP | Unknown/not selected in this cut; only later scoped genuine observations can pass. | Configuration, manual invocation or upstream feature code. |

Use `templates/templates/t3-pilot.md` for the record. Report each row as passed, failed, not selected or unknown with source/time/reason. Keep baseline, target configuration, effective configuration and observed execution separate. The result applies only to the recorded versions, selected instance and paths.
