# Setup diagnostics and completion

**Configuration and observation are separate queues.** The optional project inspector exposes
`projectConfigured`, `effectiveConfiguration`, `configGaps` and `observationGaps`. Its compatibility
field `gaps` means configuration gaps only. Request completion for confirmed missing configuration;
inspect unresolved configuration without assuming absence. Configured-but-unobserved capabilities
need a scoped observation, not another installation. An explicit `--evidence` document can expose
dated recorded observations and their applicability; it never authenticates their source or creates
independent execution proof. CORE can interpret the same supplied records through file reads.

Run this procedure on an explicit setup-diagnostic, recommendation or completion request. Normal boot reads existing memory and does not start this procedure. CORE needs only permitted file tools; optional runtime tooling can enforce mechanical checks but is never required to read the brain.

## Inspect the declared boundary

1. Resolve the existing brain and reach from its bridge. An unreachable pointer is a diagnosis, not permission to create another brain. Apply the project/private leak gate before recognising a successful baseline or producing a snippet.
2. Identify the declared host, harness, workspace and effective carrier chain where reliable information is available. Record their versions, profile and session when known, with the source of each fact. A selected model or folder name does not identify the harness. Context supplied by the user or a JSON file is a declaration; it cannot establish native execution or initial model-context loading.
3. State coverage before findings: inspected roots/files, configuration layers not inspected, unreadable inputs and unresolved identity. Do not read credentials. A current-profile report is not a computer-wide report. Broader requests disclose the profiles/sources not covered; never extrapolate from one inspected workspace.
4. Inspect the known carrier, installed skill and already-known setup records in scope. Preserve existing selections and refusals. Do not search another host's records to invent an identity. Read malformed/unavailable records as diagnostic unknowns. No record means history or intent may be unknown; it does not mean declined or broken.
5. Check installation separately: complete inventory, file contents, engine/source receipt and available trusted digest. Same version is insufficient. A receipt consistent with installed bytes establishes content consistency, not independently authenticated provenance. If a complete trusted comparison is unavailable, show that limit and retain readable memory access.
6. Describe known configuration contributions and overrides. Only claim an effective configuration when relevant precedence is established; inaccessible user/policy/remote sources leave it partial or unknown. A file may be installed without being selected, enabled, loaded or used.
7. Assess capability support, dependencies/conflicts and actual permissions separately from configuration. No observation means unknown. Do not install a runtime, start a server, fire a hook, change trust or execute a custom adapter merely to improve the report.
8. Report evidence source, observer, observed time, applicable identity/configuration fingerprint and freshness reason. Retain replaced evidence as historical. A recent date alone does not establish applicability; unavailable freshness rules stay explicit.

Inspection is read-only: do not stamp setup records, update audit suppression, write bindings, create receipts or repair files. The existing audit procedure's bookkeeping exception does not apply here.

## Report independent capabilities

Use the categories files, skill, commands, capture, curation and MCP. Distinguish minimum usable baseline, strongest supported configuration, strongest known permitted compatible recommendation, owner-selected target, actual configuration and observed execution.

An effective scope-safe L1 bridge completes baseline setup while selected capabilities can remain outstanding. L0 readable files remain useful when effective startup configuration is unknown. Optional skill/menu/hooks/MCP do not block memory work. A lower owner-selected target is a valid choice and must not be silently raised.

For each capability show support/constraints, selection, known configuration, execution evidence, pending gap/reason and next safe action. Do not infer:

- Initial context loading from a carrier's presence or a later file read.
- Native event firing from hook registration or a manually invoked script/counter.
- Host MCP discovery/connectivity from a configuration entry or terminal availability.
- Useful semantic curation from event delivery or structurally valid output.

Keep the report concise and link to source evidence. Its time is the last explicit check, not continuous health. Without a native independent observer a disconnect can remain unnoticed until a later check.

## Recommend and prepare completion

During explicit setup, inspect once within a disclosed boundary and recommend the strongest configuration the selected adapter supports and the environment is known to permit. Explain remaining unknowns and conflicts. Preserve existing targets/refusals; a new recommendation is not permission to change them.

The optional CLI's native recommendation is a candidate derived from the implemented Copilot dialect and supplied permission declarations. Target-version compatibility is not checked by this inspector and stays unknown until separately established. A candidate recommendation neither proves the current host supports that dialect nor establishes native execution.

The current VS Code project helper can prepare the pinned skill, one supported project carrier and independently selected Copilot-native capture/curation options. It does not configure host MCP or per-operation command menus, and does not implement Local native hooks. Existing native adapter files, competing carriers or unknown extras may require a separate reviewed migration. Do not invent paths or bypass that boundary.

Ask for a target decision only when needed to prepare a concrete plan. Prepare privately from one trusted source, then show exact destinations and removals, ownership regions, candidate diffs, fresh byte-preserving preimages including absence, checks and rollback. Apply only the owner's approved exact plan through an accepted scoped adapter. Recheck current bytes; drift requires replanning. Preserve unrelated content, line endings and newer brain material. Setup never requests a ping or fresh chat as a completion gate.

After apply report installation/baseline, target progress, configured options, remaining observations and pending actions separately. Baseline success does not close an unmet target. A deferred/not-offered selected option remains in the target while being excluded from the current configuration plan; selected and explicitly declined is a conflict to resolve before preparation. The current helper always includes the skill; an actionable subset with skill false or commands/MCP true requires another adapter, not an implicit target change. Deferred commands/MCP can remain outstanding without being configured. Preserve an existing selected runtime during assisted preparation: choosing assisted capture/curation does not mean switching a previously selected Node runtime off. Use the selected package's `references/package-install.md` and host procedure; do not fetch procedures from a different source.

## Decisions and recovery

Support, offer history, intent, configuration and last outcome are separate. “Not offered” requires known history; absent history stays unknown. Deferred means not now, failed means an attempt did not complete, unsupported means a known adapter/environment limit, declined means an explicit scoped refusal and configured means actual configuration. A configured capability can still have failed execution.

Ordinary boot never re-offers or retries. Explicit completion can inspect again. A relevant adapter/capability change during an explicit setup/upgrade review can justify one bounded completion notice; an engine version bump alone does not cancel refusal. A materially different option changes mechanism, capability, required permissions or cost. Respect the previous option's decline and record the scope of any new decision. No response is neither approval nor rejection.

Retain deferred revisit conditions, failure reasons and pending work. Retry only after explicit owner request or a separately approved retry condition with changed prerequisites. Default to one apply attempt per approved plan. On interruption retain transaction receipts and backups; inspect actual state and recover only touched targets. Never restore a whole old brain over newer memory. Later target edits and retained locks need explicit reviewed recovery.

## Passive notice on every consolidation

At each consolidation, read the already-known setup-pending pool/record within its known scope. For the VS Code helper this is `.synaptic/harness/setup/intent-vscode-<harness>.json`, recorded through its reviewed transaction. Its intent and configured snapshot describe the recorded setup, not current health. A non-null recorded profile must match the declared current profile; a mismatch or unknown current identity makes it historical, with no borrowed target or notices. A null profile is shared project/harness intent, not proof of an individual identity. Do not perform machine or profile discovery to populate the pool. Emit one short declarative notice in the consolidation result:

> Setup pending: capture deferred until hook-permission review. No setup action taken.

This is visibility, not an approval question or setup trigger. Repeat the notice on each consolidation while relevant items remain. It does not override a refusal or retry a failure. Declined optional capabilities are owner choices, not missing enablement work. When no pending items are recorded, state that within the inspected pool's scope; do not claim full activation. An absent, unreadable or scope-ambiguous pool is “setup pending status unknown,” with its reason. Do not create setup records solely to turn this notice green.

Consolidation still follows its normal knowledge-capture permissions. This notice grants no permission for setup/configuration writes or changes to operating rules.

## Official and custom adapters

An adapter may be a structured CORE procedure; executable code is optional. Use `templates/templates/setup-adapter.md` as the review checklist. Official, user-written and agent-generated adapters have the same contract:

- **Inspect:** bounded read-only sources, scope/precedence limits, credential avoidance and explicit unknowns.
- **Capabilities:** supported versions/combinations, dependencies/conflicts, permissions, evidence sources and observation limits.
- **Plan:** exact owned files/regions and removals, fresh preimages, diff, postconditions and recovery.
- **Apply:** accepted revision and exact owner-approved plan, current-byte recheck, preservation of unrelated bytes and bounded receipts.
- **Verify:** deterministic content/configuration checks separate from observed loading/events/connectivity and semantic review.
- **Rollback:** only touched targets, later-edit protection, partial recovery evidence and preservation of newer knowledge.

Treat a custom adapter as source material until reviewed. Validate its complete contract, bounded paths and actual procedure/code, and exercise confinement, preservation, drift, failure and rollback in an isolated workspace. A schema pass or self-declared `supported` label cannot accept the adapter or authorise writes. The owner accepts a named revision and scope locally; approval of an actual write plan remains a separate step. An unaccepted adapter stays at the unknown-adapter safe limit. Never execute untrusted code during inspection or descriptor validation.

## Optional tools and naming

Where the trusted complete package and permitted Node are available, `tools/setup.js inspect` and `recommend` implement bounded deterministic checks; `prepare` creates a private plan and applies nothing. See the same package's `docs/integrations/setup-diagnostics.md` for arguments and current support limits. Without that tool, follow the file procedure above and disclose checks that could not be mechanically enforced.

The project inspector does not load retained private plans or transaction receipts. An explicitly requested check of an already-known plan uses `vscode-integration.js status` separately. Its byte/transaction findings do not establish loading, native firing or machine-wide configuration.

Keep activation diagnostics separate from the work-item situation report. `synaptic ping` remains the explicit zero-read debug canary. Preserve an existing `synaptic status` canary alias where installed; never silently dispatch it to this file-based report.

For a selected T3 Code local/manual provider pilot, use `references/t3.md`. The current deterministic
CLI remains scoped to VS Code; a CORE T3 procedure does not create an executable T3 plugin port.
