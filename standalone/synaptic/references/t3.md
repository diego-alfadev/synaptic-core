# T3 Code project procedure

Status: source-inspected CORE adapter candidate. No T3 live-host acceptance is implied. Use only on an explicit T3 inspection, setup or pilot request. Ordinary boot reads the existing brain; it never discovers instances, offers setup or changes configuration.

This cut covers **one owner-selected local T3 environment, one existing manually configured Codex or Claude instance, and one project brain**. It reuses the provider's project instruction/skill files. It needs no Synaptic runtime or MCP. Managed ChatGPT connections, shadow homes, remote machines, worktrees, global/private reach and native capture/curation need separate reviewed scope. An out-of-scope case remains limited; never convert it to this profile silently.

## Inspect and select the instance

1. Resolve the existing brain and project root. Apply `references/host-setup.md`'s leak/reach gate. Use a synthetic owner-controlled project for the pilot, never client material or a copy of the live brain. An unreachable bridge is a diagnosis, not permission to create another brain.
2. Identify the T3 version, actual server/execution machine, selected provider kind and instance label/id, provider version, project directory and effective working directory. A provider model name is insufficient. Record each fact's source and whether it was inspected or owner-declared. An unresolved execution machine, provider or home means no concrete write plan yet.
3. Ask the owner to identify the **existing manual-login instance** from T3's selected environment/provider settings. Record only non-secret fields needed here: kind/id, binary path, configured home, whether a shadow/managed mode is used, and relevant non-secret instruction overrides. Do not dump `settings.json`, environment variables, launch arguments or provider status wholesale: they may contain secrets. Do not read `auth.json`, tokens, login caches, keychains or transcripts. Do not change login, account, trust, policy or provider selection.
4. Resolve the selected instance's effective provider home and cwd using that bounded metadata. The Codex binary/home used by T3 may differ from the terminal's. Claude uses its selected config directory. Unknown home or settings precedence remains unknown; a directory name does not prove an instance identity. Reject a shadow/managed/remote case from this thin procedure rather than traversing its special links or reading authentication files.
5. Inspect only the selected project's relevant carriers/overrides and known skill location. Identify user/policy contributions from permitted, non-secret evidence where available; otherwise list them as uninspected. Do not infer effective loading or configuration from file presence. Preserve prior owner target, refusal and deferral metadata; absent history stays unknown.

## Capabilities and exact destinations

The recommended thin profile is readable project files, one scope-safe effective bridge and an optional complete provider skill. Capture/consolidation remain explicit agent work. Menus, hooks, CLI/MCP, native model continuation and continuous health are not configured by this procedure. Preserve any existing unrelated integrations without treating their presence as proof.

Those are candidate locations, not an unconditional file allowlist. Before approval produce an exact inventory containing the selected carrier, a separate Claude import file only if needed, and **each individual file** of the selected skill package (`MANIFEST.txt`, `SOURCE.json` and the selected manifest inventory). Reject unknown extra skill files or competing engines for separate review. Do not approve a wildcard directory copy or full-file carrier replacement.

Build the candidate bridge from the selected package's `references/init.md` bridge template, using `.synaptic/BRAIN.md` and the one selected project skill's `SKILL.md` pointer. Derive command descriptions from that same package's reference summaries. For a required Claude import use only the owned `SYNAPTIC-BOOT` block specified there, and retain a pre-existing user import unchanged. Do not invent a parallel T3 command catalogue or place private absolute paths in these project files. A nonce is optional and belongs to the reviewed carrier transaction; without one a later user-requested ping can remain unknown.

The only brain-local bookkeeping destination for this thin profile is a reviewed `harness/setup/t3-<provider>.md` record (`provider` is `codex` or `claude`). Preserve a known existing record in place; do not search other host records. The record retains the selected instance facts, target, configured subset, exact inventory, decision/evidence sources and remaining unknowns; it is not a profile UUID or machine-wide registry. Its approval covers no host configuration.

**Excluded write destinations:** T3 settings/database/runtime directories; user/global provider files; environment variables; `config.toml`; provider `settings.json`; hook/MCP files; authentication; managed/shadow state. A missing baseline never authorises one of those writes. T3 launch arguments and Claude append-file injection are possible later routes, not a fallback that bypasses this cut's boundary.

A manual procedure is recoverable, not an atomic cross-process installer. On observed concurrent change stop and retain evidence rather than retrying.

Apply only the concrete plan the owner approved. Write one owned bridge block and, when selected, the exact skill inventory; preserve user-owned imports and content. Verify inventory/content against the selected source and compare actual changed paths with the approved inventory. Confirm unrelated carrier bytes, other provider instances, settings, hooks/MCP and newer knowledge stayed unchanged. A configured carrier or complete skill does not prove T3 loaded it or discovered a command.
